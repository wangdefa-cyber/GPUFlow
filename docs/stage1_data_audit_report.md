- 数据集：Alibaba `cluster-trace-gpu-v2020`
- 审计日期：2026-11-22
- 审计对象：项目 `data/` 下七张 CSV
- 完整机器可读结果：`reports/data_audit.json`
- 关联分析结果：`reports/data_relationships.json`
- 状态及 GPU 口径检查：`reports/data_quality_checks.json`

## 1. 审计结论

七张表均已正确解压，文件完整，SHA-256 与官方 README 完全一致。完整行重复记录均为 0。数据规模足以支撑真实作业、任务、实例和机器资源分析。

同时，数据并非“无缺失的完整运行日志”：

- 未完成、失败、中断和等待中的记录存在结构性空值。
- sensor 和 machine_metric 只覆盖部分实例。
- job、task、instance 三张表的 status 枚举不完全相同。
- GPU 指标存在超过 100 的原始值，必须根据机器容量解释。
- 时间字段是脱敏后的相对秒数，不能作为真实日历时间。

因此，后续导入不能简单执行 `dropna()`，否则会系统性删除失败任务、等待任务和资源不足样本，扭曲调度研究。

## 3. 数据质量发现

### 3.1 缺失值主要来自业务状态，不属于随机缺失

`pai_job_table`：

| 状态 | 行数 | start_time 缺失 | end_time 缺失 |
|---|---:|---:|---:|
| Terminated | 732,355 | 0 | 0 |
| Failed | 256,555 | 0 | 230,935 |
| Running | 62,928 | 0 | 61,867 |
| Waiting | 3,663 | 3,663 | 3,618 |

结论：

- Terminated 作业时间完整。
- Failed 作业大多没有结束时间。
- Running 作业尚未结束。
- Waiting 作业尚未开始。
- 研究成功任务执行过程时，应优先使用 Terminated；研究失败和等待行为时，必须保留空值语义。

`pai_task_table`：

| 状态 | 行数 | end_time 缺失 | plan_gpu 缺失 | gpu_type 缺失 |
|---|---:|---:|---:|---:|
| Terminated | 885,073 | 0 | 152,382 | 152,382 |
| Failed | 256,762 | 255,522 | 4,095 | 4,096 |
| Running | 115,501 | 90,325 | 63,774 | 57,546 |
| Waiting | 3,714 | 3,714 | 3,714 | 3,714 |

`pai_instance_table`：

| 状态 | 行数 | start_time 缺失 | end_time 缺失 | worker/machine 缺失 |
|---|---:|---:|---:|---:|
| Terminated | 4,757,371 | 0 | 11 | 0 |
| Failed | 969,975 | 97,316 | 888,444 | 87 |
| Running | 809,664 | 691,160 | 809,664 | 0 |
| Interrupted | 654,022 | 654,022 | 238,493 | 0 |
| Waiting | 323,840 | 323,840 | 323,840 | 323,840 |
| Ready | 7,130 | 7,130 | 7,130 | 7,130 |

结论：缺失与状态高度相关。应增加 `is_censored`、`has_started`、`has_finished`、`is_successful` 等派生标记，而不是删除记录。

### 3.2 状态枚举差异

- job：Running、Terminated、Failed、Waiting。
- task：Running、Terminated、Failed、Waiting。
- instance：Running、Terminated、Failed、Interrupted、Waiting、Ready。

后续数据库应保留 `raw_status`，另设统一业务状态映射。不得把 instance 的 Interrupted 和 Ready 强行映射成 job 的四种状态后丢失原始信息。

### 3.3 资源请求总体合理，但缺失集中

`plan_cpu`、`plan_mem`、`plan_gpu` 均没有负值。分位数显示大部分任务请求 6 vCPU、约 29.30 GB 内存、0.5 GPU。

`plan_gpu` 缺失 17.76%，`gpu_type` 缺失 17.27%。其中绝大多数缺失来自 Waiting 任务，另有部分 Running 和 Terminated 任务。

不能把“缺少 `gpu_type`”解释为“不需要 GPU”；例如终态任务中有 152,382 行 `gpu_type` 为空，但这些任务的 plan_gpu 缺失与 gpu_type 缺失几乎完全同步。

### 3.4 运行时长存在明显的右偏分布

task 表中可计算时长的 911,489 条记录：

- P50：621 秒
- P90：12,501 秒
- P95：23,731 秒
- P99：71,147.24 秒
- 最大：639,766 秒

均值会被长任务显著拉高，评价指标应同时报告中位数、P90/P95 和均值，不能只报告平均值。

所有具备 start/end 的 job、task、instance 均没有负时长。存在少量 0 秒记录：

- job：3 条
- task：118 条
- instance：29,709 条
- machine_metric：1,360 条

这些记录应保留，并在数据质量标记中注明，不应直接删除。

### 3.5 传感器与机器指标只覆盖部分实例

实例非空 worker_name 为 7,164,359 个：

- sensor 覆盖 3,033,232 个实例，约 42.14%。
- machine_metric 覆盖 2,009,421 个实例，约 28.05%。

因此不能把 sensor 或 machine_metric 的均值当成整个集群所有实例的完整使用率。

### 3.6 GPU 指标不能直接当作 0–100 单卡百分比

`pai_machine_metric.machine_gpu`：

- 原始最大值：787.41。
- 原始值大于 100 的行：1,044,545。
- 按机器总 GPU 容量归一化 `machine_gpu / (100 × cap_gpu)` 后，均值 0.2396。
- 归一化后仍有 1,593 行大于 1，其中 1,522 行大于 1.05。

这支持“`machine_gpu` 是多卡机器级汇总指标”的判断，但仍存在少量尖峰或口径异常。推荐：

1. 同时保存原始值和归一化值。
2. 不静默裁剪到 100%。
3. 在图表中提供异常值说明或单独的质量标记。
4. 在调度仿真中，仿真利用率必须由引擎计算，不能把历史 `machine_gpu` 当成仿真结果。

`pai_sensor_table.gpu_wrk_util` 最大值为 792，12,985 行大于 100，另有 1,047,917 行为 0。该字段同样需要结合实例、任务计划和 GPU 数量解释，暂不宜直接作为单卡利用率。

### 3.7 可选语义标签覆盖率低

`pai_group_tag_table`：

- `gpu_type_spec` 缺失 98.04%。
- `workload` 缺失 90.26%。

`group` 完整，可作为实例相似性/重复模式分析维度；`workload` 只能作为部分样本的补充标签，不能作为全量任务分类的强制字段。

## 4. 键与关联初步结论

- `job_name` 在 job 表唯一，并与 `inst_id` 一一对应。
- task 表的 `job_name + task_name` 唯一。
- instance 表的业务实例键建议使用 `job_name + task_name + inst_name`。
- sensor、machine_metric 的 `worker_name` 是连接实例级观测数据的关键键。
- machine_spec 的 `machine` 完整覆盖 instance 中非空机器。

主要覆盖差异：

| 关系 | 缺口 |
|---|---|
| job.job_name → task.job_name | 完全覆盖 |
| job.job_name → instance.job_name | 69 个 job 无 instance |
| task.job+task → instance.job+task | 130 个 task 无 instance |
| job.inst_id → group.inst_id | 1,530 个 job ID 无 group；1,061 个 group ID 无 job |
| instance.worker_name → sensor.worker_name | sensor 只覆盖约 42.14% |
| instance.worker_name → metric.worker_name | metric 只覆盖约 28.05% |
| instance.machine → sensor.machine | sensor 只覆盖约 91.25% |
| spec.machine → metric.machine | 约 90.67% 的规格机器出现在 metric 中 |

详细结果见 `docs/stage1_data_relationships.md`。

## 5. 推荐的数据导入方案

### 5.1 三层数据组织

**原始层**

- 保留 TAR 和 CSV，不直接修改。
- 保存 SHA-256、来源 URL、导入时间、行数、列映射。
- 只读访问；所有清洗结果写入新表。

**标准化层**

- 按官方字段名导入 SQLite。
- 增加来源、版本、质量标记和单位转换字段。
- 保留原始状态、原始时间和原始指标，不覆盖。
- 为常用关联键、时间和状态建立索引。

**分析与仿真层**

- 历史统计结果、任务样本、服务器模板、仿真实验、调度决策、资源时间线和指标结果独立存储。
- 每个仿真结果必须绑定任务集合版本、资源配置版本、算法版本和随机种子。

### 5.2 完整导入与抽样导入的比较

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 全量导入 | 最真实、可复现全量实验 | 数据库较大、页面查询和导入耗时更高 | 作为最终数据仓库方案 |
| 确定性抽样 | 开发迭代快、交互流畅 | 若抽样不具代表性会产生偏差 | 用于原型和交互演示，必须标注抽样规则 |
| 混合方案 | 小表全量、大表可选全量/分层样本 | 需要维护数据版本与样本标识 | 推荐 |

推荐混合方案：先全量导入 job、task、group_tag、machine_spec，再为大表提供“全量导入”和“按时间/用户/GPU 类型分层抽样”两种模式。抽样必须基于真实历史记录，且界面和报告中明确标注“历史数据抽样”，不得冒充全量数据。

### 5.3 导入步骤

1. 校验文件大小和 SHA-256。
2. 使用固定列映射和无表头模式读取。
3. 分块读取，每块记录源行号和导入批次。
4. 保留空值及状态，生成完整性标记。
5. 转换资源单位为核数、GPU 当量、GB。
6. 规范化时间字段为相对秒，并计算时长。
7. 写入标准化表。
8. 建立索引和约束。
9. 运行行数、键覆盖、空值分布和校验和复核。
10. 生成导入报告。

## 6. 目前缺失或尚不能确认的信息

1. 官方数据没有逐秒资源时间序列；sensor 和 machine_metric 是实例生命周期内的聚合观测。
2. 官方没有完整的未来任务到达序列，仿真任务需从历史任务回放或由用户配置生成，并明确来源。
3. 官方没有应用级碳排放、电价、能耗成本字段，不能凭空补造真实值；如后续需要，只能作为可配置假设。
4. `gpu_wrk_util` 和 `machine_gpu` 的精确采集口径仍需结合论文/官方分析代码进一步确认。
5. 69 个无 instance 的 job、130 个无 instance 的 task、1,061 个无 job 的 group 记录，其产生原因需要后续追溯。
6. 部分历史记录为等待、运行中或中断状态，不能作为完整执行样本。

## 7. 风险清单

| 风险 | 影响 | 当前处理 |
|---|---|---|
| 直接删除缺失行 | 系统性丢失失败、等待和中断样本 | 禁止；保留原始记录并增加状态标记 |
| 把相对时间当真实日期 | 时间展示和跨表解释错误 | 统一标记为脱敏相对秒 |
| 把历史 GPU 指标当仿真结果 | 混淆真实观测与模拟输出 | 三层数据分离并增加来源字段 |
| 把 GPU 百分比当 GPU 个数 | 资源约束错误 | 统一除以 100 后进入调度模型 |
| sensor 覆盖率误当全集群 | 利用率评价偏差 | 明确覆盖率和样本口径 |
| 全量 CSV 复制多份 | 占用磁盘和导入时间 | 原始只读、标准化单份、预聚合输出 |
| 仅用平均值评价调度 | 长尾和公平性问题被掩盖 | 同时报告分位数、Makespan、公平性 |
