# 项目名称：基于阿里巴巴公开GPU集群数据的GPU资源管理与智能调度仿真系统

## 一、项目背景与总体目标

请你作为一名具有丰富经验的软件架构师、Python工程师、数据工程师、算法工程师和UI/UX设计师，协助我从零开始设计、开发和完善一个完整的Web系统。

本项目基于阿里巴巴公开的GPU集群调度数据集：

官方数据仓库：
https://github.com/alibaba/clusterdata/tree/master/cluster-trace-gpu-v2020

项目目标：

按照《系统分析与设计》的完整逻辑，采用原型驱动、迭代开发的软件工程方法，构建一个集以下能力于一体的GPU集群资源管理与智能调度仿真Web系统：

1. 真实GPU集群数据导入与分析。
2. GPU服务器资源管理与配置。
3. 计算任务管理与资源需求建模。
4. GPU集群任务调度算法。
5. 任务调度过程动态仿真与可视化。
6. 多种调度策略的实验对比。
7. GPU集群运行效率分析与评价。
8. AI辅助调度决策与优化建议。

核心业务闭环：

数据导入 → 数据处理 → 资源配置 → 任务提交 → 调度决策 → 任务执行仿真 → 动态过程展示 → 效果评价 → 策略优化。

最终系统必须是一个能够实际运行、能够进行交互操作、具有真实数据支撑和可靠业务逻辑的软件系统，而不是单纯的静态数据展示页面或只有视觉效果的前端原型。

## 二、开发过程中的最高原则

### 1. 数据真实性原则

必须以阿里巴巴官方GPU Trace数据集为基础。

数据来源包括：

- pai_job_table
- pai_task_table
- pai_instance_table
- pai_sensor_table
- pai_group_tag_table
- pai_machine_spec
- pai_machine_metric

必须先检查实际下载的数据文件，分析字段定义、数据类型、数据规模、缺失值、重复值、时间格式和数据之间的关联关系。

严禁：

- 凭空编造数据字段。
- 未检查数据文件就假设数据结构。
- 为了得到更漂亮的结果而随意删除不利样本。
- 把模拟生成的数据冒充真实历史数据。
- 把历史资源监控指标直接当作未来调度结果。

必须区分三种数据：

A. 真实历史数据：来自阿里巴巴公开数据集。

B. 系统配置数据：用户自行配置的GPU服务器、资源容量和调度参数。

C. 仿真生成数据：系统根据任务需求和调度算法生成的模拟执行过程。

三类数据必须在系统中明确标记，避免混淆。

### 2. 软件工程原则

严格遵循《系统分析与设计》的开发流程：

需求分析 → 系统分析 → 系统设计 → 原型设计 → 迭代开发 → 测试验证 → 系统评价。

每个阶段都必须有明确的阶段目标、实际产出和验收标准。

不能跳过系统分析和数据库设计，直接开始堆砌代码。

### 3. 迭代开发原则

采用小步迭代的开发方式。

每次只完成一个明确的功能模块。

每个模块完成后必须：

1. 检查代码逻辑。
2. 运行对应测试。
3. 检查与其他模块的兼容性。
4. 修复已发现的问题。
5. 更新相关技术文档。
6. 明确说明本阶段完成情况。

未经验证的功能不能标记为已完成。

### 4. 技术真实性原则

所有按钮必须有真实功能。

所有图表必须有实际数据来源。

所有调度策略必须有明确算法。

所有评价指标必须有可复现的计算方法。

不允许使用静态假数据制造系统已经实现功能的假象。

## 四、系统功能模块设计

### 模块一：数据导入与数据分析中心

功能要求：

1. 支持导入官方GPU Trace数据。
2. 支持CSV文件读取。
3. 支持大型CSV分批读取，避免内存溢出。
4. 自动识别数据表结构。
5. 展示数据规模、字段信息、数据类型。
6. 检查缺失值、重复值和异常值。
7. 检查数据表之间的关联关系。
8. 展示历史任务数量、任务状态和资源需求分布。
9. 展示GPU、CPU、内存等资源的历史使用情况。
10. 提供数据导入进度与异常提示。

需要建立统一的数据字典，记录每张数据表的字段名称、数据类型、字段含义和关联关系。

### 模块二：GPU资源管理中心

建立虚拟GPU集群管理系统。

功能包括：

1. GPU服务器列表。
2. GPU型号与硬件配置。
3. 单机GPU数量。
4. CPU和内存容量。
5. GPU总容量。
6. GPU已分配数量。
7. GPU剩余数量。
8. 资源使用率。
9. 服务器运行状态。
10. 手动添加、修改和删除虚拟服务器配置。

资源模型必须支持多台服务器。

每台服务器的GPU容量、CPU容量和内存容量必须独立管理。

必须保证资源分配不能超过实际配置容量。

注意：历史数据中记录的机器规格和实际使用情况，应当与用户自行配置的仿真资源相互区分。

### 模块三：任务管理中心

建立GPU计算任务管理模块。

功能包括：

1. 历史任务查询。
2. 任务详情展示。
3. 新建仿真任务。
4. 修改任务资源需求。
5. 设置任务优先级。
6. 设置预计运行时间。
7. 查看任务排队状态。
8. 查看任务执行状态。
9. 查看任务完成情况。

任务属性至少需要考虑：

- 任务ID
- 任务名称
- GPU需求量
- CPU需求量
- 内存需求量
- 任务优先级
- 提交时间
- 预计运行时间
- 实际仿真运行时间
- 任务状态

必须区分真实历史任务和用户创建的仿真任务。

对于原始数据中不存在的属性，必须明确说明其来源，不能直接假设真实数据具有这些字段。

### 模块四：任务调度算法中心

这是整个系统的核心业务模块。

至少实现以下调度策略：

1. FIFO：先来先服务。
2. SJF：短作业优先。
3. Priority Scheduling：优先级调度。
4. Best Fit：资源最佳匹配策略。

每种策略必须有明确的算法逻辑。

调度过程必须考虑：

- GPU资源限制。
- CPU资源限制。
- 内存资源限制。
- 任务资源需求。
- 任务提交时间。
- 任务优先级。
- 任务预计运行时间。
- 服务器资源剩余情况。

必须设计合理的资源分配规则。

不能只根据GPU数量进行简单排序，而忽略CPU和内存等约束。

对于不满足资源条件的任务，必须进入等待队列，不能强行分配资源。

必须处理：

- 资源不足。
- 多任务同时等待。
- 任务完成后的资源释放。
- 任务长时间等待。
- 调度失败。
- 任务取消。
- 任务执行状态变化。

需要注意，FIFO、SJF、优先级调度和Best Fit属于不同维度的策略，必须明确各自的排序规则与资源放置规则，避免将任务排序算法和服务器分配算法混为一谈。

### 模块五：GPU任务调度仿真引擎

这是系统最重要的功能之一。

需要建立独立的仿真引擎，而不是简单地通过前端动画模拟任务运行。

仿真引擎应当具备：

1. 初始化GPU集群。
2. 加载任务队列。
3. 读取资源配置。
4. 执行调度策略。
5. 分配GPU资源。
6. 推进仿真时间。
7. 更新任务状态。
8. 释放已完成任务的资源。
9. 记录每次调度决策。
10. 生成完整仿真结果。

优先采用离散事件仿真思想。

仿真时间与现实时间相互独立。

需要支持：

- 启动仿真。
- 暂停仿真。
- 继续仿真。
- 重置仿真。
- 调节播放速度。
- 单步推进。
- 查看历史调度记录。

每次仿真必须保存：

- 使用的任务数据。
- 集群资源配置。
- 调度策略。
- 调度参数。
- 仿真开始和结束时间。
- 任务执行记录。
- 资源利用率变化。
- 最终评价指标。

确保同一实验配置可以重复运行并得到一致结果。

### 模块六：动态可视化中心

需要让用户直观理解GPU资源如何被分配。

建议实现：

1. GPU集群总体资源面板。
2. GPU服务器状态面板。
3. GPU资源使用率动态变化图。
4. 任务排队列表。
5. 任务执行甘特图。
6. 任务状态变化展示。
7. GPU资源分配过程。
8. CPU和内存资源变化。
9. 资源闲置情况展示。
10. 仿真时间轴。

动态可视化必须由仿真引擎实际输出的状态驱动。

不能使用与真实仿真状态无关的随机动画。

### 模块七：调度策略对比与效果评价

需要建立统一的调度实验评价体系。

至少统计以下指标：

| 指标 | 评价目的 |
|---|---|
| 平均任务等待时间 | 衡量任务排队效率 |
| 平均任务完成时间 | 衡量整体任务执行效率 |
| Makespan | 衡量全部任务完成所需总时间 |
| GPU平均利用率 | 衡量GPU资源利用情况 |
| CPU平均利用率 | 衡量CPU资源利用情况 |
| 内存平均利用率 | 衡量内存资源利用情况 |
| 任务完成率 | 衡量任务执行成功情况 |
| 任务超时率 | 衡量任务执行可靠性 |
| 公平性指标 | 衡量不同任务获得资源的公平程度 |

需要注意：

不同指标有不同计算口径，必须在技术文档中给出定义和公式。

所有调度策略必须使用相同的任务集合、资源配置和仿真假设进行比较。

不得通过人为调整数据来制造某一种算法表现更好的结果。

最终需要提供：

- 多策略指标对比表。
- 柱状图。
- 折线图。
- 资源利用率变化曲线。
- 任务完成时间分布。
- 实验结论分析。

### 模块八：AI辅助决策中心

在核心调度系统稳定后再实现。

AI辅助决策不要求从零训练大型语言模型。

可以优先采用：

1. 基于规则的调度建议。
2. 基于历史数据的资源需求分析。
3. 基于指标的集群拥堵预警。
4. 调度策略推荐。
5. 任务资源配置建议。
6. 仿真结果自然语言解释。

后续可以接入外部大模型API，实现：

- 当前集群状态解释。
- 调度策略推荐理由。
- 资源瓶颈分析。
- 仿真报告自动生成。
- 不同策略的优缺点分析。

AI只能提出建议，不能绕过资源约束直接修改调度结果。

所有AI建议必须具有可追溯依据，不能编造GPU使用率和实验结果。

## 七、项目测试与质量控制

必须建立完整的测试体系。

### 1. 数据测试

检查：

- 文件是否完整。
- 数据读取是否正确。
- 字段类型是否合理。
- 缺失值处理是否正确。
- 数据关联是否正确。
- 大文件读取是否稳定。

### 2. 业务测试

检查：

- 任务是否能够正确提交。
- GPU资源是否正确分配。
- 资源是否能够正确释放。
- 资源是否存在超额分配。
- 任务状态是否正确变化。
- 任务等待队列是否正确。

### 3. 算法测试

检查：

- FIFO排序是否正确。
- SJF排序是否正确。
- 优先级调度是否正确。
- Best Fit分配是否正确。
- 多资源约束是否生效。
- 相同条件下仿真结果是否可复现。

### 4. 系统测试

检查：

- 页面是否能够正常访问。
- 各模块是否正常通信。
- 数据库读写是否正常。
- 大数据读取是否导致内存溢出。
- 动态可视化是否与仿真状态一致。

每个核心模块必须有对应的测试用例。
